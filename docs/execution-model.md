# 执行模型与设计取舍

本文说明「远程执行如何确定目标」这件事的设计结论，以及为此放弃的方案和原因。实现分层见 [architecture.md](architecture.md)；用户用法见 [quickstart.md](quickstart.md)。

## 一句话结论

**每个远程工具调用自己带 `server`。** 不存在会话级「当前目标」，也不存在把原生工具透明改道到远端。

## 为什么不要「当前目标」

早期版本用一个会话级 active target 表示「现在操作哪台机器」，`@资源名` 会改写它。它在三个地方同时承担职责：

1. **执行绑定** —— 原生 `bash` 被路由到 active target；
2. **上下文状态** —— 每轮把 active target 写进提示；
3. **UI 状态** —— composer 下方显示当前目标。

三者耦合带来一组必然问题：

- 多目标任务只能逐个 `switch → 执行 → switch`，模型把时间花在切换上，人也看不出「这台到底跑了什么」；
- 多个 `@` 时 active 被清空，模型既不知道该跑哪台，也拿不到资源清单；
- 切回本地是状态变更，容易残留成「以为在本机、其实在远端」；
- 目标会漂移，事后无法从对话里复现「这条命令跑在哪台」。

所以把它整体去掉。现在：

| 场景 | 做法 |
|---|---|
| 单个目标 | `remote_bash({ server, command })` |
| 多个目标并行 | `remote_exec({ tasks: [{ server, command }] })` |
| 本机操作 | 原生 `bash` / `pwsh` / `read` / `write` / … |
| 远程文件 | `remote_read` / `remote_glob` / `remote_grep`（写需 `remoteFileWrite`） |

**每个调用的目标都写在参数里**，因此并行安全、可审计、可复现，也不存在「状态残留」。执行工具在两种宿主上都注册，避免宿主自带 shell 平台差异（Windows 宿主没有原生 `bash`）影响可用性。

## `@资源名` 是什么

**提示，不是绑定。** 用户 `@web-1` 时：

- `mentions.js` 解析出候选名字，只作为本会话的提示存储；
- `managed-context.js` 每轮把它连同资源清单写进上下文；
- 模型据此在工具参数里填 `server`。

`@` 不改变任何执行状态，所以后续无 `@` 的追问不会把命令静默带到别的机器；用户仍可随时 `@` 另一台或直接说「在本机看」。

## 上下文注入

每轮都注入一份紧凑资源清单（名称 / 方言 / 状态），而不是只在「有 active target」或「多个候选」时才注入。理由是：没有任何提示时，模型只能去读 `~/.dsh/ssh-workbench/servers.json` 猜配置——既慢，又把凭据目录暴露给模型。上下文里同时明确：

- 远程操作只能用 `remote_*` 工具，且必须显式写 `server`；
- 原生 shell / 文件工具只在本机生效；
- 目标不明确时按清单选择，或在有歧义时先问。

## 执行账本与 pill

composer 下方的 pill 是**只读投影**，不是控制器：

- 数据来自 `activity.js`（每次远程调用的 `server` / `sessionId` / `durationMs` / `outcome`），由 `execution-stats.js` 按 Session 聚合；
- 进行中的调用由 `live-executions.js` 在内存里记录，仅用于显示「正在连哪台」，不参与执行；
- 视觉对齐 DSH 内置的 Token 用量弹窗：标题 + 总次数、分隔线、目标名 → 次数；
- 不显示成功/失败、用时或模型指标（这些是 DSH 会话的私有数据，插件不伪造），不承担切换目标或打开工作台。

## 状态类批量查询的快路径

「看看几台机器状态」这类请求最大的延迟来源不是 SSH 跑命令，而是**对不可达目标的探测**：方言探测（每次最多一个 `connectTimeoutMs`）＋ `timeoutGuard` 能力探测（再一次）＋ 真正建连（再一次）。

因此 `remote_exec` 提供两个参数：

- `probe:false` —— 跳过方言与 `timeoutGuard` 探测，直接用 `facts.dialect` / 记录平台判断；
- `connectTimeoutMs` —— 按调用限制建连时间，一路透传到 broker 的 `readyTimeout`。

组合后 6 台目标里 3 台不可达时，整体从接近一分钟降到秒级；不可达任务只让自己失败，不阻塞其他任务。

## 有意的非目标

| 不做 | 原因 |
|---|---|
| 把 `read` / `write` / `edit` 透明改道到远端 | 会让「改文件」的语义取决于隐式状态，比多做几个工具危险得多；需要远程文件就用显式的 `remote_*` |
| SSHFS / 远程 IDE 式挂载 | 需要额外守护进程与权限模型，和「零安装依赖」的发布约束冲突 |
| 命令分级（allow/guarded）与风险解释 | 白名单可被 shell 语法绕过，容易制造错误的安全感；真正的边界是 SSH 权限、host-key 与 DSH 审批 |
| 插件自有审批清单 | 审批策略属于 DSH 会话预设，插件重复实现会互相矛盾 |
| 伪造模型指标（TTFT / TPS / 轮次） | 这些数据只存在于 DSH 宿主，插件无法准确获得 |

黑名单 guard 保留为兜底：同步、单调、按每个显式目标的方言逐条检查（`remote_exec` 的每个 task 都过），但它**不是权限边界**——见 [SECURITY.md](../SECURITY.md)。
